# CLAUDE.md

## Overview

`net` is a C++23 networking library (TCP/UDP sockets, DNS, URL parsing, HTTP/1.1 and HTTP/2 client and server, Prometheus/OpenTelemetry instrumentation). It is built on its own coroutine runtime. The only external dependencies are spdlog (public), glaze (private: JSON, for OTLP), Botan (private, optional: TLS) and Catch2 (tests). They come from vcpkg in manifest mode (`vcpkg.json`).

User-facing docs are `README.md` (building, and using cppnet from another CMake project) and `docs/guide.md` (the runtime, errors, lifetimes, each module, and which headers are public): keep them in step with the API (the guide's snippets were compile-checked as a throwaway example). `docs/plans/` holds design plans.

## Build

vcpkg is a git submodule (`vcpkg/`), pinned to a release that matches `builtin-baseline` in `vcpkg.json`. `cmake/vcpkg.cmake` sets the toolchain file automatically: it uses the submodule, and falls back to `$VCPKG_ROOT` only if the submodule isn't checked out. Do not pass `CMAKE_TOOLCHAIN_FILE` yourself. In-source builds are rejected.

```sh
git submodule update --init --recursive        # first time only
cmake --preset dev-clang                       # or dev-gcc, dev, dev-make, lib, lib-clang, lib-gcc
cmake --build build --config Debug
```

- `dev*` presets turn on `BUILD_TESTING` and `BUILD_EXAMPLE`. `lib*` presets build only the library.
- The `use-clang`/`use-gcc` presets add `-Wall -Wextra -Wpedantic`, and ASan+UBSan in Debug; `use-clang` also turns on libc++'s bounds checks in Debug (`_LIBCPP_HARDENING_MODE_EXTENSIVE`), so out-of-range indexes abort on macOS as libstdc++'s assertions do on Linux. Changing a preset's `*_INIT` flags needs `cmake --preset dev-clang --fresh`.
- Every preset writes to `build/` and uses Ninja Multi-Config (except `dev-make`), so binaries land in per-config dirs such as `build/test/Debug/tests`.
- Development happens on macOS and Linux. On macOS, `build` is a symlink to `build-clang/` (configured with the `dev-clang` preset, Homebrew clang), and there's no local GCC build (Homebrew's GCC lacks libasan for the presets' sanitizers): CI's GCC jobs are the GCC check there. On Linux, both presets build locally (`dev-clang` and `dev-gcc`, each with its sanitizers); point `build` at the one in use, as every preset writes to `build/`. `.clangd` reads `build/compile_commands.json`.
- Clang 23 / libc++ 23 need fmt >= 12, so spdlog must be >= 1.16.
- TLS is optional, on by default: the CMake option `NET_TLS` (and vcpkg's manifest feature `tls`, which brings in Botan); off, the build skips Botan and `src/tls/`/`test/tls/`. On, `net` defines `NET_HAS_TLS`. Botan comes from a trimmed overlay port (`ports/botan/`): its portfile's comments and `docs/plans/tls.md` ("Trimming Botan", "A trimmed Botan (part 1)") say what it patches, builds and leaves out. Any edit under `ports/` changes vcpkg's ABI hash, so every cache (CI's too) builds Botan again, about 2 minutes per configuration. A Botan module cppnet starts using goes in the portfile's module list (`configure.py` can't see algorithms looked up by name at runtime); `./tests "[tls][policy]"` fails if one is missing. A benchmark result on TLS that changes with an unrelated change's code size is worth checking against Botan's loop alignment first (the portfile's comment, and the commands in `tls.md`).
- vcpkg builds the dependencies with the same compiler (it uses `CC`/`CXX`), and its default standard library, as the project uses: e.g. libc++ with Homebrew's Clang on macOS, libstdc++ on Linux.
- Sources are collected with `GLOB_RECURSE ... CONFIGURE_DEPENDS`, so a new `src/**/*.cpp` or `test/**/*.cpp` file is picked up without editing CMake. Each subdirectory of `example/` is added automatically when `BUILD_EXAMPLE` is on.

## Tests

The tests use Catch2 v3 and build into a single `tests` executable. CTest cases are registered with `catch_discover_tests`.

```sh
ctest --test-dir build -C Debug                 # all tests
./build/test/Debug/tests                        # run directly
./build/test/Debug/tests "[uuid]"               # by tag
./build/test/Debug/tests "parse single digits"  # by test name
ctest --test-dir build -C Debug -R uuid         # via ctest regex
```

- Test files mirror the `src/` layout, for example `test/util/uuid.cpp`. Tags follow `[module][submodule][aspect]`, for example `[util][uuid][version]`. Table-driven tests use `GENERATE(test_case{...})` with designated initializers.
- Don't `co_await` inside Catch2's assertion macros (`REQUIRE(co_await x)`, `CHECK(...)`): GCC evaluates a `co_await` in the macro's never-run loop condition too, so `x` runs twice (e.g. a read consumes twice as much). Await into a local, then assert on it. The same goes for a `co_await` in one operand of `||`/`&&` when the other makes a temporary with a destructor: GCC 16 got `if (!co_await wait() || header(...) != "yes")` wrong (true with both operands false).
- Tests over real sockets and the scheduler's workers run their tasks on several threads, so an ordering a test relies on across tasks (the handler has seen the reset, the server has read the request, a helper's tasks are done with it) must be waited for, on a signal the other side sets (a word with `wait_on()`/`notify_all()`, an `async_scope`'s `join()`), never assumed to have happened by now. Each race the tests have had was one such assumption (in about 1 run in 200, so one run passes and CI fails later). Stress a new or changed concurrent test once its code has settled, not after every change: `seq 1 400 | caffeinate -s -i xargs -P 8 -I{} sh -c './build/test/Debug/tests "<spec>" >/dev/null 2>&1 || echo FAIL' | grep -c FAIL` (commas in a test's name escaped as `\,`; `caffeinate -s -i` keeps a Mac awake, so leave it out on Linux).
- A failing `REQUIRE` unwinds the test, destroying what's on its stack in reverse order: declare what the scheduler's tasks use after they could be ended some other way (e.g. a flag that a server's `serve()` task sets once it finishes) before the scheduler, whose destruction waits for them. Catch2 also runs a test case with sections once more after a section fails, to look for more, so the code outside the sections runs (e.g. spawning `serve()`) without any of them.
- Tests that need network access (and public hosts) are hidden, tagged `[.network]` (Catch2 reads it as `[.][network]`), so neither `./tests` nor ctest runs them by default. `./tests "[network]"` runs them; so does any spec naming one of their tags or names (`"[dns]"` includes them, `"[dns]~[network]"` leaves them out). The CMake option `NET_NETWORK_TESTS` (off by default; CI turns it on in every job) registers them with ctest too, labelled `network` (`ctest -L network`). The resolver's other tests use `test/dns/blocking_lookup.hpp` (a lookup that blocks until released) and the native back end's `test/dns/fake_server.hpp` (a fake nameserver on loopback, its address in an injected `dns::config`, so nothing reads `/etc` or needs the network): their comments give the lifetime rules. `run_to_completion()` waits for every blocked call, so a test that leaves a family's call blocked releases it before its task returns (a `util::defer` in the test's coroutine); a test that needs a family's answer in before going on joins the lookup with `start_resolving()` and waits on its `news()`, rather than sleeping.
- In ASan builds, the tests report leaks on Linux and (with LLVM's clang) macOS: `test/sanitizers.cpp` turns LeakSanitizer on where it isn't by default (Apple's clang doesn't support it), and suppresses known leaks in system libraries. `ASAN_OPTIONS`/`LSAN_OPTIONS` override it.
- `fuzz/` has libFuzzer targets for the parsers, codecs and HTTP/2's scheduler: each file's header says which properties it checks, besides crashes and hangs. `BUILD_FUZZING` (`AUTO`/`ON`/`OFF`, default `AUTO`) builds them with the tests when the compiler can link libFuzzer: LLVM's clang (e.g. Homebrew's) can, Apple's clang and GCC can't. Each is also a 10-second ctest run labelled `fuzz` (`ctest -LE fuzz` skips them). For a longer run: `./build/fuzz/Debug/fuzz_url -max_total_time=300 -max_len=256 <corpus-dir>`.
- `bench/` has benchmarks for implementation choices (`BUILD_BENCHMARKS`, on with the tests): each source's header says what it measures, its modes and arguments, and what it found; the plans' "Learned in" sections have the numbers behind decisions. They're only meaningful in an optimized build, and nothing runs them automatically: `cmake --build build --config Release --target bench_task && ./build/bench/Release/bench_task`. `bench/CMakeLists.txt` lists the targets; `bench_client stream` wants a link with a round trip (e.g. netem in a Linux container), and `bench_tls writes` uses the default `write_batch_size`. `bench/web/run.sh [server ...]` compares the HTTP server with Go's net/http, hyper, Bun and Node on TechEmpower's plaintext and JSON tests under `wrk` (results in `build/bench-web/`); on one laptop the JSON test is mostly bound by each request's round trip through the kernel and the scheduler, so the pipelined plaintext test separates the servers more.
- Measure by default whenever a change may affect performance (a hot path, buffer sizes, windows, copies, allocations, task hand-offs): run the relevant `bench/` target before and after (a new case if none covers it) and give the numbers in the pull request. When measuring it accurately needs a piece that doesn't exist yet (e.g. the client as well as the server), it waits until both do, and is measured then: say so in the pull request meanwhile.
- `test/test_server.go` is a throwaway Go server for manual testing against the examples. It is not part of the test suite.

## Lint / format

- `.clang-format` handles formatting. `.cmake-format` handles CMake files (all but `ports/`, which are vcpkg's ports as upstream formats them; cmake-format mangles their argument lists and comments). A comment that must keep its own line breaks (e.g. a command example) goes between `# cmake-format: off` and `# cmake-format: on`.
- clang-format is pinned to a major version (23), from PyPI, as CI installs it: locally, use the same (`pip install 'clang-format==23.*'` in a virtualenv, alongside `cmakelang==0.6.13` for cmake-format), not whatever Homebrew has, so a new major (which formats differently) is taken deliberately, with a commit that reformats. Check as CI does: `git ls-files '*.cpp' '*.hpp' '*.h' | xargs <venv>/bin/clang-format --dry-run --Werror` and `git ls-files 'CMakeLists.txt' '*/CMakeLists.txt' '*.cmake' ':!ports/' | xargs <venv>/bin/cmake-format --check`.
- `.clang-tidy` enables a broad set of checks: bugprone, cert, cppcoreguidelines, google, misc, modernize, performance, readability. `test/.clang-tidy` relaxes some checks that fire on Catch2 macros.
- To lint, run `clang-tidy -p build <file>` (a header too: it's linted as one, with a command inferred from the compile database). On macOS that's against libc++, and CI's lint is against Arch's libstdc++, which finds things libc++ hides (e.g. code under feature macros only libstdc++ defines, or throw paths inside its `std::variant`): only CI, or a lint on Linux (whose Clang builds use libstdc++ too), checks those.
- Includes follow include-what-you-use (IWYU), with the mappings in `iwyu.imp` (clang-tidy's `misc-include-cleaner` is off, as it disagrees). IWYU sees only the platform it runs on: it once dropped `config.hpp` from `epoll_loop.cpp`, which compiles epoll out on Linux without an error, so `config.hpp`'s includes carry `// IWYU pragma: keep`; after an IWYU pass, check the files with platform `#if`s and build on the other platform (or let CI). With Homebrew's LLVM, point IWYU at the same libc++ as the build, or it uses the macOS SDK's: `iwyu_tool.py -p build -- -Xiwyu --mapping_file=$PWD/iwyu.imp -Xiwyu --no_fwd_decls -nostdinc++ -isystem $(brew --prefix llvm)/include/c++/v1 -resource-dir $(clang++ -print-resource-dir)`; on Linux, against libstdc++, `iwyu_tool.py -p build -- -Xiwyu --mapping_file=$PWD/iwyu.imp -Xiwyu --no_fwd_decls` is enough. `fix_includes.py --nocomments --nosafe_headers` applies its output; then clang-format only the include blocks.
- CI (`.github/workflows/cmake.yml`, whose header explains its triggers, matrix and caches) runs on pull requests to master, weekly and by hand, not on pushes: GCC and Clang, latest major, on Arch Linux and macOS, plus `tsan` and `no-tls` builds of the tests, a `format` job, and clang-tidy (warnings as errors) on the files a change touches, so warnings already in a file get fixed when a change touches it. A job named `build` (the check `master`'s branch protection requires) passes only if every job did. So the full verification is CI's: locally, build and run the affected tests and the suite once (with ASan/UBSan, as the presets build), and leave TSan, the no-TLS build and repeated runs to CI, fixing what it finds with fixups. `.github/workflows/autobahn.yml` runs the Autobahn TestSuite against the WebSocket examples; it's optional and not part of `build` (its header says when it runs). The repo was formatted all at once (`db31961`); keep it so (format whole files you create, and only your changed lines in files that weren't clean, though all are now).

## Working on cppnet

- cppnet is a learning project, meant to be usable for side projects but not for production. Hand-rolling the runtime, parsers and protocols is the point, so don't propose libraries in their place (nor `std::regex`: the regex plan, `docs/plans/pattern.md`, is a hand-rolled Thompson NFA, with RE2 and CTRE as design references only). Park a half-built subsystem rather than leave it half-done in the tree, and recommend a reverse proxy in front of anything public.
- Git follows the user's global workflow (a branch per change, pull requests only with the user's approval, master fast-forwarded once CI passes), with cppnet's specifics: the check to wait for is `build`; master's protection also asks for an approving review, which the sole collaborator can't give, so the fast-forward push bypasses it as an admin (GitHub prints "Bypassed rule violations"); CI runs only for pull requests into master, so a stacked pull request gets CI once its base is merged and it's retargeted (fast-forwarding keeps hashes, so it needs no rebase); plan documents (`docs/plans/`) may go to master directly, still as a plain fast-forward, which then means rebasing an open pull request.
- Decisions are recorded in the plan they belong to (`docs/plans/`, in its decided questions or its stage's notes), not left in a pull request or a conversation (the first reviews' choices, from before there was a plan per area, are in `docs/plans/early-decisions.md`); work the user parks goes in `docs/plans/parked.md`, which says what's waiting for the user's go-ahead.
- Implementation is usually delegated to agents. Their briefs carry this file's rules that are easy to miss: measuring before and after, explicit waits in tests, no test hooks, the terms below. The main session reviews their work, pushes, opens pull requests and merges.
- Code conventions:
  - Failures return `std::expected<T, std::error_code>` (see the errors paragraph under Architecture); `std::optional` is for values that are legitimately absent. A new error enum is an `is_error_code_enum`, with a category whose `default_error_condition()`/`equivalent()` map it to conditions.
  - Exclusive locks are `std::scoped_lock` (not `std::lock_guard`), shared ones `std::shared_lock`.
  - Code run at scope exit is a `util::defer` (with a `noexcept` callable), not an ad-hoc RAII struct.
  - Arguments that must not be null are references, in code written or touched (no sweep of existing code). Stored pointers such as `io::scheduler*` stay pointers (a reference member makes the type non-assignable), and so do results that a `std::expected` or `std::optional` holds. A coroutine that runs detached, or outlives its caller's frame, takes neither references nor pointers to the caller's locals.
  - Running out of memory is fatal: `std::bad_alloc` isn't caught, and clang-tidy's `bugprone-exception-escape` ignores it, `bad_array_new_length` and `length_error` (its `IgnoredExceptions` list is comma-separated; with `;` it silently ignores nothing).
  - Aggregates' members have default initializers (`{}`), so designated initializers name only what they set.
  - `util::string_map` exists for heterogeneous lookup: extend it rather than work around it.
  - A peer must never control the server: a busy peer, not just an idle one, mustn't keep `close()`/`join()` or a resource bound from finishing. Enforce deadlines by the clock, not only in waits; a small fixed cost per read for that is acceptable.
- Tests:
  - No test hooks in library code (test-only accessors, parameters, friends) without a very good reason: tests observe behaviour, through the public API or the other side (e.g. what the server sees). Ask the user before adding one. Saving real-time waits was reason enough once (`tls::detail::verify_for()`'s time, so no test sleeps past a certificate's expiry). Every path gets a test, not just an argument that it works.
  - Retries in tests are the exception. For an ordering race, remove it at its source, in the library (the server listening in its constructor fixed a connect racing `serve()`) or in the test's structure; retry only where nothing better exists (an external process, the OS), and say why there.
  - A negative check (nothing sent, no reset, the peer hasn't closed) starts its timed wait only after an explicit signal that the thing would already have happened; an ordered proof (e.g. a PING round trip) is better than a timer where there is one. Catch2 isn't thread-safe: tasks on workers record, the test's thread asserts. When a wait for tasks that point into a frame times out, abort what they block on, then wait for them without a deadline.
- Measuring:
  - Use standard terms in plans, pull requests and reports: a benchmark case (a scenario a bench measures), a metric (time, CPU time, allocations per unit), target cases (those a change is expected to improve, named before measuring).
  - Benchmarks are load-sensitive: measure on an otherwise idle machine (nothing else building or benchmarking), interleaving the before and after rounds. Numbers from different machines or CPUs aren't comparable, so a baseline is rerun on the machine measuring the change. A Mac in maintenance sleep stalls long runs unless they're under `caffeinate -s -i`.
  - The coroutines plan (`docs/plans/coroutines.md`) sets how a change's results are judged (its keep/drop bar and statistics).
- Parallel work runs in separate git worktrees, each with its own build directory (`cmake --preset ...` in each; vcpkg's binary cache makes that quick), never in another agent's checkout. Benchmarks and stress runs don't share the machine with them.

## Architecture

Everything lives in `namespace net`, with sub-namespaces that match the directories (`net::io`, `net::coro`, `net::http`, `net::util`, ...). Public headers are in `include/<area>/`. Implementations are in the matching path under `src/`. Headers are included relative to `include/`, for example `#include "io/scheduler.hpp"`.

Each area's design, decisions and status are in its plan (`docs/plans/`), its use in `docs/guide.md`, and its internals in the headers' and sources' comments (the `NOTE`s say why). Read them before changing an area, and keep them current rather than describing the area here.

- **Coroutines (`coro/`)**: `coro::task<T>` (lazy; awaiting resumes it directly, so `co_await`s that finish without suspending don't grow the stack), `ready_task()` for results without a coroutine, `coro::operation`/`adapter`/`stepper` for waits without a coroutine frame, `thread_pool` (its idle workers poll for I/O), `notifier`, `async_scope`. Plan: `coroutines.md`.
- **Scheduler (`io/`)**: `io::scheduler` ties the event loop (`epoll_loop` on Linux, `kqueue_loop` on macOS/BSD; IOCP has only its macro, `NET_HAS_COMPLETION_PORTS`), the pool and an `async_scope` together, and owns waits and their deadlines, futex-style `wait_on()`/`notify_*()`, `call_at()` and stop tokens per wait. Plans: `handler-cancellation.md`, `middleware.md` (stage 4, `call_at()`).
- **Sockets and streams (`socket.hpp`, `tcp.hpp`, `udp.hpp`, `listen.hpp`, `io/`)**: non-blocking sockets with deadlines, timeouts and stop tokens; `io::reader`/`io::writer` and their wrappers (buffered, limited); `tcp_socket::connect()` resolves and connects with Happy Eyeballs.
- **Errors**: `std::expected<T, std::error_code>`, with the library's own error enums compared against conditions (guide's "Errors"; `early-decisions.md`).
- **HTTP (`http/`)**: the server (HTTP/1.1, and HTTP/2 over cleartext or ALPN; tunnels for upgrades), the client (connection pool, HTTP/2, redirects), routers and middleware (`http::chain`, `http::timeout`), HPACK and Structured Fields. HTTP/1.1 decoding (`http11.cpp`) is deliberately strict, as request smuggling exploits ambiguity between the server and a proxy. Byte-wise parsing reads from `buffered_reader::buffered()`/`consume()` rather than `co_await`ing each byte. Plans: `http2.md`, `middleware.md`, `client-redirects.md`, `handler-cancellation.md`; HTTP/3 is parked in `http3.md`.
- **WebSockets (`websocket/`)**: client and server, over HTTP/1.1 and HTTP/2 (extended CONNECT). Plan: `websockets.md`.
- **DNS (`dns/`)**: the resolver (system and native back ends; the default picks per name), its errors, and the message codec. Plan: `dns-resolver.md`.
- **TLS (`tls/`, with `NET_HAS_TLS`)**: `tls::stream` over a `tcp_socket`, with Botan kept private. Plan: `tls.md`.
- **Instrumentation (`instrument/`)**: Prometheus metrics, OpenTelemetry trace context and OTLP/JSON (glaze, private), and `http_metrics`/`http_tracing` middleware; spans go to a callback, as there's no exporter yet.
- **The rest**: `url`, `ip_addr`/`ipv4_addr`/`ipv6_addr`, `encoding/` (base64, hex), `util/` (small self-contained utilities).

`example/http-server/main.cpp` shows a typical program's setup (signals blocked before threads start, the scheduler, `server.close()` then `join()` on a signal, then `scheduler.shutdown()`); `run_to_completion(task)` suits a program that runs one task (`example/http-get`).

### Invariants and gotchas

- Layering: `encoding` → `util` → `coro` → `io`. `util/` depends only on `encoding/` and `config.hpp`'s platform macros; keep it that way, so the layers don't form cycles.
- Never request stop while holding a scheduler shard's lock, `timers_mu` or an HTTP/2 connection's `mu`: stop callbacks take them (`connection_mutex` checks it in debug builds). Lock order: a shard's lock, then `timers_mu`.
- Coroutine frames: Clang elides one (HALO) only for a coroutine called directly in a `co_await`, outside a loop, never through a wrapper that isn't a coroutine or through an indirect call (`coroutines.md`, "Which calls Clang elides"). Keep the awaiter holding the handle rather than the task, keep `task`'s destructor `[[gnu::always_inline]]`, and make a coroutine whose frame must be its own `[[gnu::noinline]]` (`task.hpp`'s notes). A function that can often finish without waiting returns a `ready_task`, and calls a coroutine only when it must wait.
- Botan's endpoints agree on TLS 1.3 unless one is limited, so a TLS 1.2 test limits one side.
- `example/websocket-echo` (port 9001) is what Autobahn's `fuzzingclient` tests by hand: `docker run --rm -v $PWD:/ab -w /ab crossbario/autobahn-testsuite wstest -m fuzzingclient -s /ab/fuzzingclient.json`, the config's server `ws://host.docker.internal:9001`, in a scratch directory, never the repository. Started in the background from a non-interactive shell, it ignores SIGINT (inherited as ignored): stop it with SIGTERM.
