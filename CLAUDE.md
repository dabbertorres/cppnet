# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Overview

`net` is a C++23 networking library (TCP/UDP sockets, DNS, URL parsing, HTTP/1.1 and HTTP/2 client and server, Prometheus/OpenTelemetry instrumentation). It is built on its own coroutine runtime. The only external dependencies are spdlog (public), glaze (private: JSON, for OTLP), Botan (private, optional: TLS) and Catch2 (tests). They come from vcpkg in manifest mode (`vcpkg.json`).

User-facing docs are `README.md` (building, and using cppnet from another CMake project) and `docs/guide.md` (the runtime, errors, lifetimes, each module, and which headers are public): keep them in step with the API (the guide's snippets were compile-checked as a throwaway example). `docs/plans/` holds design plans.

## Build

vcpkg is a git submodule (`vcpkg/`), pinned to a release that matches `builtin-baseline` in `vcpkg.json`. `cmake/vcpkg.cmake` sets the toolchain file automatically: it uses the submodule, and falls back to `$VCPKG_ROOT` only if the submodule isn't checked out. Do not pass `CMAKE_TOOLCHAIN_FILE` yourself. In-source builds are rejected.

```sh
git submodule update --init --recursive        # first time only
cmake --preset dev-clang                       # or dev-gcc, dev, dev-make, lib, lib-clang, lib-gcc
cmake --build build --config Debug
```

- `dev*` presets turn on `BUILD_TESTING` and `BUILD_EXAMPLE`. `lib*` presets build only the library.
- The `use-clang`/`use-gcc` presets add `-Wall -Wextra -Wpedantic`, and ASan+UBSan in Debug; `use-clang` also turns on libc++'s bounds checks in Debug (`_LIBCPP_HARDENING_MODE_EXTENSIVE`), so out-of-range indexes abort on macOS as libstdc++'s assertions do on Linux. Changing a preset's `*_INIT` flags needs `cmake --preset dev-clang --fresh`.
- Every preset writes to `build/` and uses Ninja Multi-Config (except `dev-make`), so binaries land in per-config dirs such as `build/test/Debug/tests`.
- Development happens on macOS and Linux. On macOS, `build` is a symlink to `build-clang/` (configured with the `dev-clang` preset, Homebrew clang), and there's no local GCC build (Homebrew's GCC lacks libasan for the presets' sanitizers): CI's GCC jobs are the GCC check there. On Linux, both presets build locally (`dev-clang` and `dev-gcc`, each with its sanitizers); point `build` at the one in use, as every preset writes to `build/`. `.clangd` reads `build/compile_commands.json`.
- Clang 23 / libc++ 23 need fmt >= 12, so spdlog must be >= 1.16.
- TLS is optional, on by default: the CMake option `NET_TLS` (and vcpkg's manifest feature `tls`, which brings in Botan); off, the build skips Botan and `src/tls/`/`test/tls/`. On, `net` defines `NET_HAS_TLS`. Botan comes from an overlay port (`ports/botan/`, named in `vcpkg.json`'s `vcpkg-configuration`): vcpkg's, with a patch adding includes Botan 3.12 omits that libc++ 23 no longer pulls in (`libcxx-missing-includes.patch`), and builds it with `-falign-loops=64` on x64 (the portfile's comment says why: Intel's JCC erratum on Skylake-derived cores made Botan's TLS 1.3 padding scan about 25% slower whenever unrelated code linked before it moved the loop onto a 32-byte boundary; aligned, its speed no longer depends on that; check its place with `otool -tV -p __ZN5Botan3TLS12Record_Layer11next_recordEPNS0_12Cipher_StateE` on macOS, `objdump -d --disassemble=_ZN5Botan3TLS12Record_Layer11next_recordEPNS0_12Cipher_StateE` on Linux, each on the built Botan library). A benchmark result on TLS that changes with an unrelated change's code size is worth checking against that first. The overlay also trims Botan (`docs/plans/tls.md`, stage 4's first part): `configure.py --minimized-build` with only the modules cppnet uses (one list in the portfile, a comment per group: TLS 1.2/1.3 and the PQ hybrids, Go's key exchange groups, X.509/PEM/ECDSA (with RFC 6979)/RSA and its paddings, the system trust store (keychain, or a bundle), AES-GCM/ChaCha20-Poly1305, SHA-2/HMAC/HKDF/TLS 1.2's PRF, the system RNG, and the CPUs' versions by wildcard, e.g. `aes_*`), and without Botan's command-line tool. Algorithms Botan looks up by name at runtime are invisible to `configure.py`, so a module added to cppnet's use goes in the list, and `test/tls/stream.cpp`'s handshake per group, cipher suite and kind of certificate (`[tls][policy]`, through the internal `tls::detail::make_client_context()` with `detail::policy_limits`, IANA code points) fails if one's missing. The policy (`src/tls/tls.cpp`) offers only Go's groups (X25519, P-256/384/521, and Botan's three ML-KEM hybrids) and ECDHE, so cppnet behaves the same over a whole Botan (e.g. a project's own vcpkg port). Its client's first ClientHello has key shares for the first hybrid and the first elliptic curve group allowed (X25519MLKEM768 and X25519, as Go and Chrome; overriding Botan's `key_exchange_groups_to_offer()`, whose default is X25519's alone), so Botan's server (cppnet's), which picks a hybrid whenever the client lists one, needs no HelloRetryRequest (`docs/plans/tls.md`, "Key shares (after part 3)"); `policy_limits::key_shares` overrides the choice in tests. A fresh build of the trimmed Botan still takes a few minutes (here, about 2 per configuration, debug and release). On Apple platforms `net` also links CoreFoundation and Security, for Botan's keychain trust store.
- vcpkg builds the dependencies with the same compiler (it uses `CC`/`CXX`), and its default standard library, as the project uses: e.g. libc++ with Homebrew's Clang on macOS, libstdc++ on Linux.
- Sources are collected with `GLOB_RECURSE ... CONFIGURE_DEPENDS`, so a new `src/**/*.cpp` or `test/**/*.cpp` file is picked up without editing CMake. Each subdirectory of `example/` is added automatically when `BUILD_EXAMPLE` is on.

## Tests

The tests use Catch2 v3 and build into a single `tests` executable. CTest cases are registered with `catch_discover_tests`.

```sh
ctest --test-dir build -C Debug                 # all tests
./build/test/Debug/tests                        # run directly
./build/test/Debug/tests "[uuid]"               # by tag
./build/test/Debug/tests "parse single digits"  # by test name
ctest --test-dir build -C Debug -R uuid         # via ctest regex
```

- Test files mirror the `src/` layout, for example `test/util/uuid.cpp`. Tags follow `[module][submodule][aspect]`, for example `[util][uuid][version]`. Table-driven tests use `GENERATE(test_case{...})` with designated initializers.
- Don't `co_await` inside Catch2's assertion macros (`REQUIRE(co_await x)`, `CHECK(...)`): GCC evaluates a `co_await` in the macro's never-run loop condition too, so `x` runs twice (e.g. a read consumes twice as much). Await into a local, then assert on it. The same goes for a `co_await` in one operand of `||`/`&&` when the other makes a temporary with a destructor: GCC 16 got `if (!co_await wait() || header(...) != "yes")` wrong (true with both operands false; `test/http/server_scheduling.cpp`'s `held::start()`).
- Tests over real sockets and the scheduler's workers run their tasks on several threads, so an ordering a test relies on across tasks (the handler has seen the reset, the server has read the request, a helper's tasks are done with it) must be waited for, on a signal the other side sets (a word with `wait_on()`/`notify_all()`, an `async_scope`'s `join()`), never assumed to have happened by now. Each race the tests have had was one such assumption (in about 1 run in 200, so one run passes and CI fails later). Stress a new or changed concurrent test once its code has settled, not after every change: `seq 1 400 | caffeinate -s -i xargs -P 8 -I{} sh -c './build/test/Debug/tests "<spec>" >/dev/null 2>&1 || echo FAIL' | grep -c FAIL` (commas in a test's name escaped as `\,`; `caffeinate -s -i` keeps a Mac awake, so leave it out on Linux).
- A failing `REQUIRE` unwinds the test, destroying what's on its stack in reverse order: declare what the scheduler's tasks use after they could be ended some other way (e.g. a flag that a server's `serve()` task sets once it finishes) before the scheduler, whose destruction waits for them. Catch2 also runs a test case with sections once more after a section fails, to look for more, so the code outside the sections runs (e.g. spawning `serve()`) without any of them.
- Tests that need network access (and public hosts) are hidden, tagged `[.network]` (Catch2 reads it as `[.][network]`), so neither `./tests` nor ctest runs them by default: e.g. `test/dns/resolver.cpp`'s real lookups of public names with the system back end (`google.com`, `nothing.invalid`), `test/dns/native.cpp`'s with the native back end and the machine's own configuration (also a public CNAME chain each, `www.github.com` and `www.microsoft.com`), and TLS's handshakes with public servers (not a TLS 1.2 server without Extended Master Secret: that one's local, see `tls/` below). `./tests "[network]"` runs them; so does any spec naming one of their tags or names (e.g. `"[dns]"`: `"[dns]~[network]"` leaves them out). The CMake option `NET_NETWORK_TESTS` (off by default; CI turns it on in every job) registers them with ctest too, by a second `catch_discover_tests` with the spec `[network]` and the ctest label `network` (`ctest -L network`). The rest of the resolver's tests use `test/dns/blocking_lookup.hpp`, a `dns::resolver` whose `system_lookup` hook blocks until released (also used by `test/tcp.cpp` and the HTTP client's tests): it must outlive the scheduler, and be released before it's destroyed (a `util::defer` declared after the scheduler). A lookup of both families is two calls (one per family: `started`/`finished` count calls), each answering with its family's part of `answer` (or `EAI_NONAME`), and each family can be released on its own (`release(protocol::ipv4)`); `run_to_completion()` waits for every call, so a test whose connect or caller leaves a family's call blocked must release it before its task returns (e.g. a `util::defer` in the test's coroutine). Tests that need a family to be in before doing something else join the lookup with a resolution of their own (`start_resolving()`, see `dns/` below) and wait on its `news()`, rather than sleep. The merging tests (`[dns][resolver][merge]`) run their callers on a pool of one worker, so a caller has joined its lookup (which it does without suspending) by the time another task sees it counted. The native back end's tests (`test/dns/native.cpp`, `[dns][native]`; but the network's) use `test/dns/fake_server.hpp`, a fake nameserver on loopback (a listener on a port the OS chooses, and a UDP socket bound to the same port) answering through a handler per test (`answer_from(zone)`, or by hand with `reply_to()`: drops, delays (a delayed UDP reply holds up the queries after it, unless it's `fake_reply::apart`, sent by a task of its own), TC, FORMERR, wrong IDs or questions, any RCODE), whose received queries (with their source port, TCP or not, and time) the test checks; the resolver gets its address in an injected `dns::config`, so nothing reads `/etc` or needs the network. It must be declared after the scheduler (and after what its handler uses); its sockets live in state its tasks share. `test/dns/config.cpp` tests the configuration's parsers on strings, and its cache on files in a temporary directory.
- In ASan builds, the tests report leaks on Linux and (with LLVM's clang) macOS: `test/sanitizers.cpp` turns LeakSanitizer on where it isn't by default (Apple's clang doesn't support it), and suppresses known leaks in system libraries. `ASAN_OPTIONS`/`LSAN_OPTIONS` override it.

## Lint / format

- `.clang-format` handles formatting. `.cmake-format` handles CMake files (all but `ports/`, which are vcpkg's ports as upstream formats them; cmake-format mangles their argument lists and comments). A comment that must keep its own line breaks (e.g. a command example) goes between `# cmake-format: off` and `# cmake-format: on`.
- clang-format is pinned to a major version (23), from PyPI, as CI installs it: locally, use the same (`pip install 'clang-format==23.*'` in a virtualenv, alongside `cmakelang==0.6.13` for cmake-format), not whatever Homebrew has, so a new major (which formats differently) is taken deliberately, with a commit that reformats. Check as CI does: `git ls-files '*.cpp' '*.hpp' '*.h' | xargs <venv>/bin/clang-format --dry-run --Werror` and `git ls-files 'CMakeLists.txt' '*/CMakeLists.txt' '*.cmake' ':!ports/' | xargs <venv>/bin/cmake-format --check`.
- `.clang-tidy` enables a broad set of checks: bugprone, cert, cppcoreguidelines, google, misc, modernize, performance, readability. `test/.clang-tidy` relaxes some checks that fire on Catch2 macros.
- To lint, run `clang-tidy -p build <file>` (a header too: it's linted as one, with a command inferred from the compile database). On macOS that's against libc++, and CI's lint is against Arch's libstdc++, which finds things libc++ hides (e.g. code under feature macros only libstdc++ defines, or throw paths inside its `std::variant`): only CI, or a lint on Linux (whose Clang builds use libstdc++ too), checks those.
- Includes follow include-what-you-use (IWYU), with the mappings in `iwyu.imp` (clang-tidy's `misc-include-cleaner` is off, as it disagrees). IWYU sees only the platform it runs on: it once dropped `config.hpp` from `epoll_loop.cpp`, which compiles epoll out on Linux without an error, so `config.hpp`'s includes carry `// IWYU pragma: keep`; after an IWYU pass, check the files with platform `#if`s and build on the other platform (or let CI). With Homebrew's LLVM, point IWYU at the same libc++ as the build, or it uses the macOS SDK's: `iwyu_tool.py -p build -- -Xiwyu --mapping_file=$PWD/iwyu.imp -Xiwyu --no_fwd_decls -nostdinc++ -isystem $(brew --prefix llvm)/include/c++/v1 -resource-dir $(clang++ -print-resource-dir)`; on Linux, against libstdc++, `iwyu_tool.py -p build -- -Xiwyu --mapping_file=$PWD/iwyu.imp -Xiwyu --no_fwd_decls` is enough. `fix_includes.py --nocomments --nosafe_headers` applies its output; then clang-format only the include blocks.
- CI (`.github/workflows/cmake.yml`) runs on pull requests (to master), and weekly (Mondays 06:00 UTC) and by hand (`workflow_dispatch`) on master, not on pushes: master is fast-forwarded to a pull request's commit once it has passed, so a push run would test it again; the weekly run saves the caches new pull requests restore (a pull request's own are scoped to it) and catches a new compiler between pull requests. It builds (Debug, Ninja, vcpkg, `NET_NETWORK_TESTS` on in every job) and runs ctest with the latest major GCC and Clang: on Linux in an `archlinux:base-devel` container (on `ubuntu-26.04`), as Arch packages them first; on `macos-26`, Homebrew's `gcc` and `llvm`. Neither pins a version, so a new major is picked up as it's packaged. It caches vcpkg's built packages (its `files` binary cache, keyed by OS, compiler version, the vcpkg submodule's commit and a hash of `vcpkg.json` and `ports/`) and ccache's cache of the project's compilation (saved each run), with `actions/cache`'s separate restore and save steps, so a run whose tests fail still saves them. A `format` job checks every C++ file with clang-format (PyPI's, pinned to 23) and every CMake file but `ports/`' with cmake-format (0.6.13, from cmakelang), both in one virtualenv; the Linux Clang job lints, after building, the `.cpp` files a change touches that are in the compile database, and the headers it touches in the project's own directories (`include/`, `src/`, `test/`, `bench/`, `example/`, `fuzz/`: clang-tidy infers a header's command from a nearby source's), against the PR's base (on pull requests only), with clang-tidy and warnings as errors, so warnings already in a file get fixed when a change touches it. Two more matrix entries, on Linux with Clang, build only the tests: `tsan` (Debug with `-fsanitize=thread`, the tests once in a random order; a report fails its test) and `no-tls` (`NET_TLS=OFF`). So the full verification (ThreadSanitizer, the build without TLS, the whole suite on four toolchains) is CI's: locally, build and run the affected tests and the suite once (with ASan/UBSan, as the presets build), and leave TSan, the no-TLS build and repeated runs to CI, fixing what it finds with fixups. A job named `build` (the check `master`'s branch protection requires) passes only if every job of the matrix, and `format`, did. A second workflow, `.github/workflows/autobahn.yml` (`docs/plans/websockets.md`, stage 10), runs the Autobahn TestSuite (`crossbario/autobahn-testsuite`, pinned by tag and digest) against the WebSocket examples: `fuzzingclient` against `example/websocket-echo` and `fuzzingserver` against `example/websocket-autobahn`, sections 1-7 and 9 (12-13 are permessage-deflate). It's optional: by hand (`workflow_dispatch`), weekly (Wednesdays 04:17 UTC), and for pull requests that change it or `.github/autobahn/` (its configurations and `check.py`) only; not part of `build`. One job on the bare `ubuntu-26.04` runner (a job container has no Docker): the examples are built (Release, Clang, `NET_TLS=OFF`, sharing the `no-tls` job's vcpkg cache) and run in an `archlinux:base-devel` container of its own, on the host's network as the suite's containers are; `check.py` fails a case whose `behavior` or `behaviorClose` isn't OK, NON-STRICT or INFORMATIONAL (Autobahn's ungraded outcome), or a report without the expected 300 cases; the reports are the run's artifact. ## Working on cppnet

- cppnet is a learning project, meant to be usable for side projects but not for production. Hand-rolling the runtime, parsers and protocols is the point, so don't propose libraries in their place (nor `std::regex`: the regex plan, `docs/plans/pattern.md`, is a hand-rolled Thompson NFA, with RE2 and CTRE as design references only). Park a half-built subsystem rather than leave it half-done in the tree, and recommend a reverse proxy in front of anything public.
- Git follows the user's global workflow (a branch per change, pull requests only with the user's approval, master fast-forwarded once CI passes), with cppnet's specifics: the check to wait for is `build`; master's protection also asks for an approving review, which the sole collaborator can't give, so the fast-forward push bypasses it as an admin (GitHub prints "Bypassed rule violations"); CI runs only for pull requests into master, so a stacked pull request gets CI once its base is merged and it's retargeted (fast-forwarding keeps hashes, so it needs no rebase); plan documents (`docs/plans/`) may go to master directly, still as a plain fast-forward, which then means rebasing an open pull request.
- Decisions are recorded in the plan they belong to (`docs/plans/`, in its decided questions or its stage's notes), not left in a pull request or a conversation (the first reviews' choices, from before there was a plan per area, are in `docs/plans/early-decisions.md`); work the user parks goes in `docs/plans/parked.md`, which says what's waiting for the user's go-ahead.
- Implementation is usually delegated to agents. Their briefs carry this file's rules that are easy to miss: measuring before and after, explicit waits in tests, no test hooks, the terms below. The main session reviews their work, pushes, opens pull requests and merges.
- Code conventions:
  - Failures return `std::expected<T, std::error_code>` (see the errors paragraph under Architecture); `std::optional` is for values that are legitimately absent. A new error enum is an `is_error_code_enum`, with a category whose `default_error_condition()`/`equivalent()` map it to conditions.
  - Exclusive locks are `std::scoped_lock` (not `std::lock_guard`), shared ones `std::shared_lock`.
  - Code run at scope exit is a `util::defer` (with a `noexcept` callable), not an ad-hoc RAII struct.
  - Arguments that must not be null are references, in code written or touched (no sweep of existing code). Stored pointers such as `io::scheduler*` stay pointers (a reference member makes the type non-assignable), and so do results that a `std::expected` or `std::optional` holds. A coroutine that runs detached, or outlives its caller's frame, takes neither references nor pointers to the caller's locals.
  - Running out of memory is fatal: `std::bad_alloc` isn't caught, and clang-tidy's `bugprone-exception-escape` ignores it, `bad_array_new_length` and `length_error` (its `IgnoredExceptions` list is comma-separated; with `;` it silently ignores nothing).
  - Aggregates' members have default initializers (`{}`), so designated initializers name only what they set.
  - `util::string_map` exists for heterogeneous lookup: extend it rather than work around it.
  - A peer must never control the server: a busy peer, not just an idle one, mustn't keep `close()`/`join()` or a resource bound from finishing. Enforce deadlines by the clock, not only in waits; a small fixed cost per read for that is acceptable.
- Tests:
  - No test hooks in library code (test-only accessors, parameters, friends) without a very good reason: tests observe behaviour, through the public API or the other side (e.g. what the server sees). Ask the user before adding one. Saving real-time waits was reason enough once (`tls::detail::verify_for()`'s time, so no test sleeps past a certificate's expiry). Every path gets a test, not just an argument that it works.
  - Retries in tests are the exception. For an ordering race, remove it at its source, in the library (the server listening in its constructor fixed a connect racing `serve()`) or in the test's structure; retry only where nothing better exists (an external process, the OS), and say why there.
  - A negative check (nothing sent, no reset, the peer hasn't closed) starts its timed wait only after an explicit signal that the thing would already have happened; an ordered proof (e.g. a PING round trip) is better than a timer where there is one. Catch2 isn't thread-safe: tasks on workers record, the test's thread asserts. When a wait for tasks that point into a frame times out, abort what they block on, then wait for them without a deadline.
- Measuring:
  - Use standard terms in plans, pull requests and reports: a benchmark case (a scenario a bench measures), a metric (time, CPU time, allocations per unit), target cases (those a change is expected to improve, named before measuring).
  - Benchmarks are load-sensitive: measure on an otherwise idle machine (nothing else building or benchmarking), interleaving the before and after rounds. Numbers from different machines or CPUs aren't comparable, so a baseline is rerun on the machine measuring the change. A Mac in maintenance sleep stalls long runs unless they're under `caffeinate -s -i`.
  - The coroutines plan (`docs/plans/coroutines.md`) sets how a change's results are judged (its keep/drop bar and statistics).
- Parallel work runs in separate git worktrees, each with its own build directory (`cmake --preset ...` in each; vcpkg's binary cache makes that quick), never in another agent's checkout. Benchmarks and stress runs don't share the machine with them.

## Architecture

Everything lives in `namespace net`, with sub-namespaces that match the directories (`net::io`, `net::coro`, `net::http`, `net::util`, ...). Public headers are in `include/<area>/`. Implementations are in the matching path under `src/`. Headers are included relative to `include/`, for example `#include "io/scheduler.hpp"`.

### Coroutine runtime (`coro/`, `io/`)

All I/O is coroutine-based. Nearly every I/O function returns `coro::task<T>` (lazy: `initial_suspend` is `suspend_always`). Awaiting a task resumes it directly, and the awaiter only suspends if the task does (an atomic flag decides which side continues the awaiter), so a loop of `co_await`s that complete without suspending doesn't grow the stack, even where symmetric transfer wouldn't be a tail call (GCC without optimizations, or with ASan). It costs an atomic exchange per `co_await`; `task.hpp`'s comment has the trade-off, and `bench/coro/task.cpp` measures it. `coro::ready_task<T>(value)` makes a task that has already finished, without a coroutine (calling a coroutine allocates its frame): functions that can often finish without waiting return one, and only call a coroutine when they must wait. `buffered_reader::read`/`buffered_writer::write` (when the buffer suffices), `socket::read`/`write` (when the syscall doesn't block), `limit_reader`/`limit_writer` (when what they wrap finished without a coroutine), and since the coroutines plan's stage 4 `chunked_reader::read` (inside a chunk, or with the next size line buffered; the boundary's slow path `read_slowly()`), the client's `pooled_body` reads (its bookkeeping through an adapter), `string_reader::read`, `connection_pool::acquire()` (a free connection or stream is claimed when it's called, not when awaited; waiting or connecting is `acquire_waiting()`), the server's `room_for_connection()` below `max_connections`, the client's request head (`request_encode()`/`request_encode_head()` format it into the buffered writer's `prepare()`d space when it fits, as `response_encode` does), and `io::write_all` of one piece (the writer's own task; it once seemed to make TLS writes 16-19% slower, which was Botan's loop alignment, below) do; keep the awaiter holding the handle rather than the task, or Clang stops eliding frames of coroutines that are awaited directly. A task can also be an operation (`coro::operation<T>`, made a task by `operation_task(op)`): its state lives elsewhere, it's claimed for one task at a time (`try_claim()`, released when its result is taken or its task is destroyed unawaited; and `cancel()`ed, by the awaiting coroutine's promise, if that coroutine is destroyed while it waits, so it isn't resumed), and the task's awaiter starts it and takes its result, again without a coroutine. `task`'s destructor is `[[gnu::always_inline]]`: a coroutine's body destroys the tasks it awaits on its exception-cleanup path too, a cold call site where Clang inlines only what costs at most 45, and a destructor left out of line there takes the handle where the elision can't see it, so the awaited coroutine's frame isn't elided. The destructor's cost depends on `T` (a ready task's result's destructor) and on what it calls, so without the attribute elision hung on a few points of it: a virtual call in it lost 77 of 78 elisions (which had been put down to the call being opaque), and tasks of e.g. `std::expected<std::string, std::error_code>` (cost 135) were never elided. With it, what the destructor calls may be opaque (a virtual call keeps every elision), and 84 calls in `src/`, `bench_request` and `bench_task` are elided rather than 78. A coroutine whose frame must be its own (freed as it returns) is `[[gnu::noinline]]`, as eliding it needs its ramp inlined: `server::serve_requests()`, so a cleartext HTTP/2 connection's HTTP/1.x state goes before HTTP/2 is served (`serve_connection()`'s frame stays 5 KB, not 12.5). How Clang elides a coroutine's frame into its caller's (HALO), checked with `-Rpass=coro-elide -Rpass-missed=coro-elide` (Clang 23, `-O3`): by default (`coro-elide`) only a coroutine called directly in a `co_await`, and not inside a loop; never through a wrapper that isn't a coroutine (e.g. one returning a `ready_task` or a coroutine's task), nor an indirect call (e.g. the handler). `[[clang::coro_await_elidable]]` on `task` switches to another pass (`coro-annotation-elide`, remarks `-Rpass=coro-annotation-elide`) that elides calls by how often they run: those in loops, but not ones that run once, unless `-mllvm -coro-elide-branch-ratio=0` (an internal LLVM option). So the frames a request that has to wait still allocates (the handler's, and `decode_reading`'s for a head that comes in pieces) aren't elided (since the coroutines plan's stage 2 the server and the client wait for a head with the reader's `fill()` first, then decode it, without a coroutine if it came whole) (`buffered_reader::fill()` no longer makes one: since the coroutines plan's stage 1 it finishes a fill that waits with a `coro::adapter`, `include/coro/adapter.hpp`, an operation the reader holds, rather than the `fill_after` coroutine; since stage 3 the other wrappers are too: `limit_reader`/`limit_writer` and the server's default response with adapters, and loops over waits (`buffered_reader::read()` past the buffer, `buffered_writer`'s `flush()` and large writes, `flush_before_read`, the WebSocket's large frames, `sending`) with a `coro::stepper` (same header: a step makes of each inner task's result the result, or the next inner task; steps whose inner tasks finish at once run inline; ones that wait resume the stepper's driver, one 56-byte coroutine per stepper made the first time it waits and kept, so a second flush or large write while one waits is `device_or_resource_busy`; an optional `Released` hook runs once it's free, which the WebSocket's wire hand-off (`wire_leaving`, `let_go()`) uses), their slow paths `[[gnu::noinline]]` so `read()`/`write()`/`flush()` stay small); the attribute could take `decode_reading` (needing `serve_connection` to await it directly, defined in a header), at the cost of bigger frames (eliding cold calls would put e.g. the ~4.5 KB rare-path coroutines in each connection's frame) and an unstable flag, so it's parked; frame pooling is the other option.

- **`coro::thread_pool`**: worker threads that resume `std::coroutine_handle`s from one shared queue. A `thread_pool::poller` can be attached (one per pool): then an idle worker waits for I/O itself rather than sleeping (as Tokio's do), one at a time, and runs the first coroutine it readies, waking sleeping workers only for the rest. A busy worker polls without blocking every `poll_interval` (61) jobs, if no one else is polling. No one polls while a worker runs a coroutine that doesn't suspend, so one sleeping worker (the standby; `attach()` wakes one to be it, as workers usually fall asleep before there's a poller) waits with a timeout (`watchdog_interval`, 10 ms, as Go's sysmon), and takes over polling if no one is; then it wakes another to be the standby. Each worker also has a slot (Tokio's LIFO slot, Go's `runnext`): `resume()` called on one of the pool's own workers puts the coroutine (a batch's last; the rest are queued) in that worker's slot, which it runs once what it's running returns to it (never inline, so `notifier`'s rule holds), before the queue, with no lock and no wakeup; a coroutine it displaces is queued, waking a worker. At most `max_next_runs` (2) slot runs in a row, then the queue: Tokio's 3 slowed `bench_request`'s 8 request bodies at once by 4 to 15%, as chains of slot runs held up the queue, where what I/O readied waits (2 measured as the base; 1 as well, with less of the gain elsewhere). Slot runs count toward `poll_interval` and in `num_jobs` (`size()`); shutdown runs what's in the slots as what's queued. `schedule()`/`yield()`, and resumes from other threads (`run()`'s, `run_blocking`'s, a foreign one), are queued. So hand-overs between tasks (a `notifier`'s waiters, `wait_on`'s notifies, stop callbacks' cancellations, `deregister_handle()`, `request_stop()`, the HTTP server's watch, what `call_at`'s calls resume, on the polling worker) stay on the worker, while the poller's readiness and expired timers go through the queue as before (the worker that polled runs the first). Nothing steals a slot but the watchdog: a coroutine still in the same slot (the same put, by its `puts` count) at two looks `watchdog_interval` apart is queued for the others (`watch_slots_locked()`, by the standby on its timeout and by a worker back from a poll); a worker polling while no standby's asleep polls with a `watchdog_interval` timeout (`poller::poll()` takes an optional timeout; a standby woken while a poll has none wakes the poller, which polls again with one), and a pool without a poller has a standby too once a slot's been used (the first use wakes one). So a coroutine left in the slot of a worker that never comes back (a coroutine whose awaits are all ready) runs within 10 to 20 ms, on a pool of two workers or more; on one worker it waits until that coroutine returns, as what's queued does. Go's way, waking an idle worker for each slot put to take it after 3 us, was measured too and gave back most of the gain (a wakeup per hand-over: HTTP/2 WebSocket 16 B round trips 48.7 us against 33.6). Tests: `test/coro/thread_pool.cpp`'s `[slot]` (`test_poller` takes the timeout). Tasks still shouldn't block (use `run_blocking`).
- **`coro::notifier`**: a futex-style counter for coroutines (read `value()`, check a condition, `co_await wait(seen)`; `notify()` changes the value and resumes waiters on the pool, never inline, as the notifier may hold a lock they take (if the pool refuses them, as it's shutting down, the program terminates); `close()` wakes them for good). Its own lock, no deadlines (see `bench_notifier`); its first two waiters are held in place (a list past them), so a wait doesn't allocate, and nothing of it is touched once one's resumed (which may destroy it). For HTTP/2's connections, and TLS streams' flushes.
- **`coro::async_scope`**: owns detached tasks. `spawn(task)` counts the task and destroys its frame when it finishes; `join()`/`join_blocking()` wait until the scope is empty; a closed scope refuses new tasks. `acquire()` takes a `lease`, which counts as a task while held: for work the scope doesn't own (e.g. the scheduler's tasks that use a server), which joining it must still wait for.
- **`io::detail::event_loop`**: the OS-specific part, selected at compile time from the platform macros in `include/config.hpp`. It is `epoll_loop` on Linux and `kqueue_loop` on macOS/BSD (IOCP is declared but not implemented). It only reports readiness: implementations satisfy the `io::EventLoop` concept in `io/event_loop.hpp` (`add`/`remove` a handle, `wait(events, timeout)`, and `interrupt()` from any thread). Handles are registered once, edge-triggered for reads and writes (kqueue `EV_CLEAR`, epoll `EPOLLET`): a handle is reported when it becomes ready, so callers must try their syscall until it would block before waiting.
- **`io::scheduler`** ties the event loop, the thread pool and an `async_scope` together, and owns the waiting coroutines (at most one reader and one writer per handle) and their deadlines. Handles are split by fd over 64 shards, each with its own lock, registrations and timers (whose earliest deadline is an atomic, for `run()`: a new or moved deadline, e.g. `retime()`'s for a waiting read's `set_read_deadline()`, is stored there before `note_deadline()` decides whether to interrupt the loop, as the loop, woken, reads it again; the other way round, a woken loop could find the old one and sleep past the new); an event that arrives with nothing waiting sets the direction's `ready` flag, which the next wait consumes instead of suspending (so a wait makes no syscall). Sleeps and `wait_on` have their own lock (`timers_mu`); lock order is a shard's, then `timers_mu`.
  - `spawn(task)` runs a task on the pool; the scheduler owns it until it finishes.
  - `co_await wait(fd, op)` / `wait_until(fd, op, deadline)` / `wait_for(...)` suspend until the handle is ready, returning a `std::error_code` (`timed_out`, `operation_canceled`, ...). The awaiter holds its own result.
  - A `scheduler::handle_operation` is a wait that performs an operation (e.g. a `recv()`) once the handle's ready, rather than resuming the waiting coroutine to try it: `perform()` runs under the handle's shard lock, and returns false to keep waiting (e.g. `EAGAIN`, or a write that's made only some progress, which may move its deadline with `set_deadline()`). A socket's `read`/`write` try the syscall first, and if they'd have to wait, return a task of the socket's `read_operation`/`write_operation` (one each per socket, so a second concurrent read fails with `device_or_resource_busy`, and a socket must outlive the reads and writes waiting on it).
  - The scheduler attaches itself to its pool as the poller, so the workers dispatch readiness and timeouts (from when it's constructed, whether or not `run()` is called). `run()` blocks until the scheduler is stopped and its tasks have finished; if the pool already polls for another scheduler, `run()` polls for this one on the calling thread instead (and resumes what it readies on the pool).
  - `request_stop()` refuses new tasks and cancels every pending (and future) wait with `operation_canceled`, so tasks unwind by themselves. `shutdown()` also waits for that, and is called by the destructor; `shutdown()` throws `std::logic_error` if called from one of the pool's workers (e.g. one of its own tasks, which would wait for itself; use `request_stop()`), so the destructor terminates there.
  - `run_to_completion(task)` spawns the task, runs the scheduler on the calling thread until it finishes, then stops the scheduler.
  - `wait_on(word, expected, deadline)` / `notify_one(word)` / `notify_all(word)` let one task wait for another, futex-style, on a `std::atomic<std::uint64_t>`: change the word, then notify, so a notification between checking a condition and waiting isn't lost. `sleep_until(deadline)` sleeps. Both are canceled by `request_stop()`.
  - `call_at(deadline, func)` calls a `noexcept` function at a deadline instead of resuming a coroutine (`docs/plans/middleware.md`, stage 4: `http::timeout`'s timer, no task per request). It returns a `scheduler::call<F>` (deriving from `call_base`, which holds a function pointer to invoke it, its `stage` and its timer), the caller's, constructed in place (guaranteed elision; not movable), so nothing's allocated: its constructor schedules it once `func` is in place. Calls have their own `timer_queue<call_base>` (`calls`; `timer_queue` is a template on what waits, `waiter` or `call_base`, whose spare nodes are reused) under `timers_mu`, counted by `next_deadline()`. `expire_timers()` returns whether a call is due, and then `poll()` runs `make_calls()` after the locks are released (stop must never be requested holding a shard lock or `timers_mu`, and calls may request stop): one at a time, each taken off the queue (`calling`) under `timers_mu`, called without it, then marked `called` under it, notifying `calls_done` (a `std::condition_variable` on `timers_mu`). So calls run on the thread polling (a worker, or `run()`'s thread). `call_base::cancel()` removes a pending call (returning true), or waits on `calls_done` for one being made on another thread (a `thread_local` says which call this thread is making, so a call canceling itself doesn't wait), so its captures may go once it returns; the destructor cancels. `request_stop()` drops pending calls, and `call_at` on a stopping scheduler schedules nothing (both under `timers_mu`).
  - A single wait can be canceled with a `std::stop_token` (`docs/plans/handler-cancellation.md`, stage 1): `wait`/`wait_until`/`wait_for`/`wait_on`/`sleep_until` overloads taking one as their last argument return a `stoppable_wait_operation` (the token-less ones and their `wait_operation` are unchanged, so their frames don't grow), which registers a `std::stop_callback` (`canceler`, calling `stop_wait()`) in `await_suspend` *before* taking the wait's lock: the callback takes that lock, completes the waiter with `operation_canceled` if it's registered (then resumes it on the pool, after unlocking), or sets the waiter's `canceled` flag (in padding, checked under the lock beside `stopping`) if it hasn't begun; `await_resume` resets the callback (whose destructor waits for one running elsewhere). So stop must never be requested holding a shard lock or `timers_mu` (e.g. in `perform()`). A `handle_operation` holds its own callback (`begin(..., stop)`, deregistered by `end_wait()` before its result is taken, or `cancel_wait()`). `request_stop()` then stops `scheduler::stop_token()` (holding no locks). `run_blocking(func, stop)` returns `std::expected<R, std::error_code>`: `func` isn't started if stop was requested (`operation_canceled`), and gets the token if it takes one; it's never interrupted. `run_blocking` returns a `scheduler::blocking_call<R>` (not a `coro::task`: an awaitable, awaited once, that owns its state), whose state is a frame of its own (`blocking_job()`, a coroutine with its own promise, `blocking_call::promise_type`: `func` as its parameter, the result or exception in `detail::blocking_outcome`, and an atomic of two flags, `done` and `left`; one allocation, as the old coroutine's frame), shared by the call and the blocking thread, so the awaiting coroutine may be destroyed while it waits: `await_suspend()` counts the call (`begin_blocking()`, `blocking_calls`) and queues the job on the blocking pool; the job checks `left` first (`blocking_start`: gone, it frees itself without running `func`), and at its end (`blocking_end`) `finish()` sets `done`: if `left` was set it frees itself (result and `func` with it), else resumes the awaiting coroutine on the workers (`scheduler::resume()`, never inline on the blocking thread); either way then `end_blocking()`. The call's destructor, while it waits, `leave()`s (sets `left`), and frees the state only if `done` was set already; never awaited, it frees it without `func` running. Await the call directly for its one allocation; where a task is needed (`spawn()`, an `async_scope`, a `coro::task<R>` variable) it converts implicitly (`operator coro::task<R>() &&`, the user's decision) to `as_task()`'s task, a small coroutine whose frame holds the call and awaits it (a second allocation), as safe to destroy unawaited (`func` never runs, the state freed with the frame) or mid-call (the frame's call `leave()`s) as the call. Whatever `func` refers to (rather than owns) must outlive its run, not just the awaiting coroutine. `run_blocking`'s pool has `scheduler::options::blocking_threads` threads (4 by default; `scheduler(workers, options, logger)`); its users are the system resolver's lookups. `shutdown()` waits, after the scope's tasks, for `blocking_calls` to drop to 0 (counted from `await_suspend()` until the job's done with the scheduler, its state freed if abandoned; the count's declared before `blocking`, so it outlives the threads that notify it), so a `func` whose caller is gone is still waited for. Tests: `test/io/scheduler.cpp`'s `[run_blocking]` (`[abandon]`: a caller destroyed while `func` runs, and while it waits for the one blocking thread, and `shutdown()` waiting for an abandoned `func`; `[stop]`: stop while queued; `[task]`: the conversion awaited (result and exception), spawned, destroyed unawaited (and the call itself), and its caller destroyed mid-call). `bench_blocking` (`bench/io/blocking.cpp`) measures a call's round trip and allocations.
- Sockets are non-blocking: `socket::read`/`write` try the syscall first and only wait on `EAGAIN` (as an operation the scheduler performs, see above). Per-socket deadlines (`set_read_deadline` etc.) bound how long they wait altogether, and timeouts (`set_read_timeout` etc.) bound how long they may go without progress; `set_stop_token()` cancels waiting reads/writes (registered by the socket's operations, only when they wait), a canceled read having read nothing (`perform()` and the cancel both run under the shard lock), and `tls::stream::set_stop_token()` forwards to its socket (a canceled TLS write is a `write_failure`, as any failed write). `socket::wait_writable()` (`docs/plans/http2.md`, stage 6's third part) waits until the kernel counts the socket writable, writing nothing (`coro::task<io::result>`, count 0): a `poll()` that doesn't wait first (a ready task if writable), else the socket's write operation claimed in its own mode (`claim_writable()`, `only_writable`), whose `perform()` polls rather than sends, so a stale `ready` flag or any event is checked again, the write deadline, timeout and stop token apply, and it can't overlap a write (`device_or_resource_busy`, whichever's second); POLLERR/POLLHUP count as writable (the write says why). `tcp_socket::set_notsent_lowat(bytes)` sets TCP_NOTSENT_LOWAT (0 off, clamped to `INT_MAX`, `not_supported` where it's not defined): Linux's `send()` stops at the mark and its `poll()`/EPOLLOUT say writable under half of it; macOS's `send()` ignores it and its `poll()`/kqueue apply it (with Nagle on, not before a segment's unsent), so a writer waits for `wait_writable()` before writing (part 4: the HTTP/2 server's writer, under HTTP; over TLS, `tls::stream::wait_writable()`, through the stream's flush queue, and `http::detail::wait_writable(conn)` picks). Its tests (`test/socket.cpp`, `[socket][wait-writable]`) fill a loopback connection until `poll()` says not writable and nothing's in flight (Linux: SIOCOUTQ == SIOCOUTQNSD; macOS: TCP_CONNECTION_INFO's bytes sent against written less SO_NWRITE), as macOS's loopback delivers apart from `send()`, so "not writable" right after a burst is often undone by an acknowledgement still to come. `listener::make(scheduler, host, port)` binds and listens, returning `std::expected` (the constructors bind without listening, and throw `std::system_error`); `listener::accept()` returns `std::expected<tcp_socket, std::error_code>`, failing with `operation_canceled` after `shutdown()`. `udp_socket::connect(scheduler, ip_addr, port)` (a client's: `read`/`write` with its one peer, an empty datagram reading as `end_of_stream`) and `udp_socket::bind(scheduler, ip_addr, port)` (a server's: `receive_from()`/`send_to()`, an empty datagram being one) return `std::expected` at once; they replaced the resolving constructors (`docs/plans/dns-resolver.md`, stage 1). Both go through `socket`'s protected `read_from()`/`write_to()`, the socket's read and write operations with an address (`recvfrom()`/`sendto()`), so deadlines, timeouts and the stop token apply. `socket::local_port()` throws as `listener::local_port()` does. `ip_addr` converts to and from `sockaddr` with `detail::to_sockaddr()`/`from_sockaddr()` (`sockaddr.hpp`, internal; `detail::socket_address` is a `sockaddr_storage` and its length; no IPv6 zone, as `ip_addr` has none). `url::parse`, `ip_addr::parse` and `io::readline` return `std::expected` too (`util::result` is gone).

It waits for each attempt inline (`wait_connected()` until the next is due) until one outlasts the delay: only then is there a race (`race`, behind a `shared_ptr` held by `keep_racing()` and each attempt: a `util::linked_stop_source` from `options.stop` that stops the attempts, an atomic word `changes`, and under its `mu` the `winner`, `over`, the failures' count, the latest to fail and the last error), so the usual case (the first attempt connects within the delay) allocates nothing more than before. The attempt that outlasted it, and every later one that doesn't finish at once, is a spawned task (`racing_attempt()`, owning its socket and a share of the race, so it may outlive `connect`): it `claim()`s the race (unless it's over: then it closes its socket) or `fail()`s, then bumps `changes` and `notify_all()`s; `keep_racing()` reads the word, `look()`s (taking a winner, which makes the race `over`), and waits with `wait_on(changes, seen, next attempt due or the deadline, options.stop)`, so the delay is that wait's deadline (no `call_at` or separate sleep). However `racing()` ends (its frame too), a `util::defer` calls `race::end()`: `over`, a winner not taken closed, then stop requested on the race's source (holding no locks), so losers close themselves. `attempt_delay` 0, or a single address, is `one_at_a_time()`, as before: in order, each with Go's share of the timeout (`detail::attempt_deadline()`: what's left over the addresses left, at least 2 s, never past the end), a timed-out attempt moving on to the next. - Errors are `std::error_code`s, as the standard library intends: reported precisely (errno in `std::system_category()`, or the library's own code enums: `io::errc` (`end_of_stream`, `no_progress`), `tls::errc` and alerts, `dns::errc`, `gai_category()`'s, `http::route_error`, `http::client_errc`), and compared against conditions, whose equivalences then run: `std::errc`, or `io::status_condition` (`closed`: the end of the stream, a reset/abort/broken pipe, or TLS's `stream_truncated`; `timed_out`), or `dns::condition` (`not_found`: `dns::errc::name_not_found`/`no_address`, `EAI_NONAME`/`EAI_NODATA`; `temporary_failure`: `server_failure`, `EAI_AGAIN`/`EAI_FAIL`; its category's `equivalent()` knows `gai_category()`). Comparing two conditions is exact, which is why results never carry them. Failures return `std::expected<T, std::error_code>`; I/O results are `io::result{count, std::error_code}`, not thrown. Code that means precisely the end of the stream compares with `io::errc::end_of_stream`; "however it ended" with `status_condition::closed`.

### I/O abstractions

`io::reader` and `io::writer` are abstract interfaces with coroutine `read`/`write` over `std::span<std::byte>`. `net::socket` implements both and registers its fd with the scheduler. `tcp_socket`, `udp_socket` and `listener` (`listen.hpp`) build on `socket`. The composable wrappers in `io/` (`buffered_reader`/`buffered_writer`, whose reads and writes larger than the buffer go past it with one read or write of what's wrapped for all that's left, `limit_reader`/`limit_writer`, `discard_writer`, `string_reader`/`string_writer`, `io::buffer`) and HTTP's `chunked_reader`/`chunked_writer` all implement these interfaces (a body cut short fails with `std::errc::connection_aborted`, rather than ending: `chunked_reader`'s, and `limit_reader`'s whose reader ends before its limit, unless it's `limit_reader::mode::up_to`, a cap, as for a response body that ends with the connection, or the HTTP/2 client's request bodies, whose length it checks itself; `chunked_reader::keep_trailers(trailer_fields*)` keeps the trailer section's fields, but those `http::trailer_allowed()` refuses (Go's `ValidTrailerHeader` list: `If-*` and 21 names), replacing what the headers held, before `call_at_end()`'s callback, and leaves them empty if the section fails; null, the default, checks and drops them; either way the section's limited to `max_trailers` (8 KiB) and `http11::max_fields` lines, `value_too_large` past either; `chunked_writer::finish(const trailer_fields* trailers = nullptr)` writes the allowed ones in the last chunk, into an `io::buffered_writer`'s buffer without a coroutine when it fits (as heads are), and fails with `invalid_argument`, writing nothing, if any field's invalid (`valid_fields()`)), so protocol code is written against `reader`/`writer` rather than sockets. Tests rely on that to use string readers and writers.

### HTTP (`http/`)

`http::server` listens from when it's constructed (so connections made before `serve()` runs are queued, not refused), accepts on a `listener` (one it's given, e.g. from `listener::make()`, or one on `server_config`'s host and port, whose constructors throw if it can't listen), and runs `serve_connection` per connection (backing off, from 5 ms to 1 s, when `accept` fails, e.g. with EMFILE): over TLS if `server_config::tls` (a `tls::server_context`, made with `server_context::make()`) is set, whose handshake has a deadline of its own `header_read_timeout`; a connection that agrees on an ALPN protocol besides `http/1.1` is closed; `server_request::tls_version` tells handlers the version agreed on (`detail::tls_version(conn)`, from `stream::version()`, set once per HTTP/1.1 connection, kept by `clear()`, and per HTTP/2 stream), `tls::version::none` in cleartext and without TLS; `server_request::peer_certificates` the client's certificate chain (`detail::peer_certificates(conn)`: null unless the client sent one, which it does only to a context that asks; set beside `tls_version` per HTTP/1.1 connection, and once per HTTP/2 connection, in its constructor, shared by its streams). It serves a `detail::connection`, as the client's pool holds. It holds a lease on its own `async_scope` for `serve()` and each connection (which are the scheduler's tasks), so `~server` closes and waits for them: it must not be destroyed from one of the scheduler's tasks. `serve()` takes its lease when it's called, passing it to its task (`accept_connections`), as `serve_connection` gets its own: taken when the task starts, a server destroyed before then (e.g. as a test fails) would find nothing to wait for. `close()` works before the task starts too (`closed` is separate from `serving`), and the task then returns at once. `close()` stops accepting, and ends the open connections gracefully: it requests stop on a `std::stop_source` (`closing`). An HTTP/1.1 connection's `std::stop_callback` (in `connection_state`) moves its phase (an atomic: `idle` waiting for a head or HTTP/2's preface, `busy` serving a request, `closing`) to `closing`, and calls `socket::shutdown_read()` (so reads find the end of the stream) only if it was idle; a busy one finishes its request (its response gets `Connection: close` if its head isn't sent yet, through `response_writer`'s `close_after` token), then closes, as `end_request()`'s CAS from busy fails; a head read after an idle shutdown (e.g. buffered) isn't served, as `start_request()`'s CAS from idle fails. Pipelined requests after it aren't served. A cleartext connection that turns out HTTP/2 moves to busy (or closes, if closing came first) before unregistering its callbacks, as HTTP/2 registers its own (a graceful drain). TLS handshakes get the stop token too (`stream::accept()`'s `accept_options::stop`), as their socket is out of the server's reach. Handlers get a `std::stop_token` in `server_request::stop` (`docs/plans/handler-cancellation.md`, stage 2), which the server sets before each handler call (`clear()` keeps it; middleware may swap it): HTTP/1.1 has one `std::stop_source` per connection (`connection_state::stop`, made by `serve_http1()` once the connection isn't HTTP/2), stopped by `abort()`, by the connection's end (a `util::defer`), and by the client leaving while a handler waits (stage 4: the watch, `connection_state`'s comment: once the handler has suspended (`handler_runs`, an awaiter marking an atomic gate) and its body is at its end (an `io::end_callback` from `limit_reader`/`chunked_reader`, set by `http11::call_at_body_end()`), with nothing buffered after it, a per-connection watcher coroutine, resumed on the pool, `fill()`s the connection's reader with `flush_before_read::hold()` on and no read timeout; the end of the stream (half-close too, as Go), a reset or close_notify stops the source, data ends the watch; when the handler's done the server flushes, sets the head's deadline on the read already waiting (a socket's read deadline is its read operation's `handle_operation::limit_deadline()`, under the shard lock, so it applies to a waiting read from any thread), and awaits the watcher through an atomic handoff; paths that end the connection abandon the watch with a deadline of now. Handlers that never suspend aren't watched (eagerly watching cost the socket test 9%). TLS: `accept_options::hold_close_reply` (the server sets it from the handshake) makes TLS 1.3 hold back the answer to the client's close_notify (Botan's `tls_peer_closed_connection()` returns false) until `shutdown()`/`close()`, as RFC 8446 6.1 allows, so a response still goes out; on TLS 1.2 Botan answers at once whatever it returns, as RFC 5246 7.2.1 requires, so a handler stopped by close_notify can't respond; HTTP/2 connections `release_close_reply()`); HTTP/2 one per stream (`http2_stream_base::stop`, the server's streams only), stopped when the stream fails (but not once it's a tunnel, whose reads and writes find its failures, as a switched HTTP/1.1 connection's do). `server::abort()` is `close()` plus stopping `aborting`, whose callbacks shut every HTTP/1.1 connection's reading side, busy or not (bodies being read fail), and stop its source, and stop every HTTP/2 stream's (`stop_handlers()`; streams started after get stopped sources); `~server` aborts (after unregistering its callback on `scheduler::stop_token()`, which also aborts), then waits; HTTP/2 connections still drain gracefully. `join()` is a task awaiting `running` (serve() and the connections). A handler stopped without answering gets no response from the server (no default 200, no 500 if it throws, logged at debug): HTTP/1.1 closes, HTTP/2 resets with CANCEL (unless the stream failed); `http_metrics`/`http_tracing` record such requests (token stopped before the final response) as 499, not an error, if the client's side stopped them, or 503 if the server aborted (`server_request::aborted`, a copy of the server's `aborting` token, set once per HTTP/1.1 connection and per HTTP/2 stream; whether the server aborted, not a reason). After an error response, the server lingers (over TLS, after `stream::shutdown()`'s close_notify). Sizes are options (none a 0-means-default; out of range refused: the server's and `http::client`'s constructors throw `std::invalid_argument`, from `check_sizes()` in `server.cpp` and the pool's `checked()`; buffers at least `detail::min_buffer_size`, 1 KiB, windows `detail::valid_window()`, 65535 to 2^31-1, both in `http2_config.hpp`): `server_config::read_buffer_size`/`write_buffer_size` (16 KiB, `connection_state`'s reader and writer, a WebSocket's over HTTP/1.1 too), `http2_read_buffer_size` (32 KiB, `http2_connection_base`'s `read_size`, through `http2_options`/`http2_client_options::read_size`), `http2_stream_window` (65535, the session's `local.initial_window_size`; the connection's window `clamp(streams × window, 1 MiB, 2^31-1)`); `client_options::read_buffer_size` (4 KiB, `pooled_body`'s reader), `write_buffer_size` (16 KiB: HTTP/1.1's `request_encode()`/`request_encode_body()` `body_buffer` argument, `http11::default_body_buffer`, and HTTP/2's `send_body()`, `http2_client_options::body_buffer_size`), `http2_read_buffer_size`, `http2_stream_window` (4 MiB, as Go's; the connection's 1 GiB); the 4 KiB head writer, `max_output`, `max_ahead`, chunk sizes, MAX_FRAME_SIZE, HPACK's and the linger/discard limits stay constants. Interim (1xx) responses (`docs/plans/http2.md`, stage 5's first part; `status::EARLY_HINTS`) keep the headers for the final response, and go out at once: over HTTP/1.1 `send()` flushes the connection's writer after one (`send_interim()`, a coroutine; the handler's own write, as a watch's read doesn't flush), over HTTP/2 a HEADERS frame; none to an HTTP/1.0 client (`send()` returns a `discard_writer`); `send(status::SWITCHING_PROTOCOLS)` throws `std::system_error` (`not_supported`): only switching sends a 101. Router handlers are `request_handler`s (`coro::task<void>(server_request&, response_writer&)`), which may take the request as const; the router sets `server_request::route` to the pattern that matched (e.g. `/users/:id`), and handlers read parameters with `req.path_value("id")`. `route` and `path_values` are views (of the router's patterns, and of the path, or `path_value_storage` for decoded values), so routing doesn't allocate; `path_values` is a `util::small_vector`. Routes are `route_pattern`s (`http/route_pattern.hpp`): a string literal is checked by a `consteval` constructor, so a bad pattern doesn't compile; `route_pattern::parse()` checks one made at runtime. `http::static_router` (`http/static_router.hpp`, made by `make_static_router(GET("/users/:id"_route, h), group("/api"_route, ...))`) routes the same way, with patterns as template arguments (`util::fixed_string`): its tree is built at compile time (a perfect hash per node), route conflicts fail to compile, and handlers may take `params<"/users/:id">` (by value) for `p.get<"id">()`, checked at compile time. Literal segments win over parameters, without backtracking; a parameter never matches an empty segment; GET handles HEAD unless the route has its own (the server drops HEAD response bodies, via `io::discard_writer`); 405s carry `Allow`. Middleware (`http/middleware.hpp`, `docs/plans/middleware.md`; stages 2 and 3 done) is a value with `template<class Next> coro::task<void> operator()(server_request&, response_writer&, Next& next) const`, composed at compile time by `http::chain(layers..., handler)` (outermost first) into an `http::chained_handler`, copyable when its items are; `next(req, resp)` runs the rest, at most once (not enforced), and a layer may answer without it, or `return next(req, resp);` without a coroutine of its own. The `next` objects aren't coroutines: empty CRTP bases of the chain (`detail::chain_next`, reaching the following item with `std::get`), so the chain stays copyable and nothing points into itself, and Clang elides the inner layers' frames (and a handler's the innermost calls directly, but never a router's handlers) into the outermost one's, which the server allocates (as it calls the chain through `request_handler`). `http::next_handler` (two pointers, as `std::function_ref`) is what a non-template `operator()` takes, for a body in a `.cpp`: called indirectly, so the rest isn't elided. The `middleware<M, Next = next_handler>` and `handler<H>` concepts check a chain's items. Middleware on some routes only runs after routing (it sees `route` and the path values), never for 404s and 405s: `static_router`'s `use(layers...)`, first in a `group(...)` (or in `make_static_router`, for every route; anywhere else a `static_assert` fails), makes each of the group's routes a `chained_handler` of its own copies of the middleware (outer groups' first; built with the router; move-only middleware only on one route) ending in `detail::route_call`, which calls the handler with its `params`: the layers and the handler are elided into the outermost layer, so it costs no allocation over the handler alone (unless the handler is a function pointer, called indirectly; a lambda calling it is elided), where `chain()` around a router costs one (`bench_request` measures both). The runtime router's `use(layers...)` applies to every route under the router or subrouter it's called on, whenever and however they were added: each node holds its `layers` (its parents', then its own, type-erased `std::function`s behind `shared_ptr`s, updated through the subtree by `insert_layer()`), and each route a heap-held `route_handler` (so the `next_handler`s it keeps, one per step, stay put as the router moves) whose layers are called with a `const next_handler&` to the next step: nothing per request but the layers' frames, one allocation each. Middleware passes request-scoped values to handlers in `server_request::extensions` (a `util::type_map`). `http::timeout{&scheduler, duration}` (`http/timeout.hpp`, stage 4, which is also the cancellation plan's stage 5) gives the rest of its chain a deadline: a `util::linked_stop_source` from `req.stop` swapped into `req.stop` (restored after, also on a throw), stopped by a `scheduler::call_at()` at the deadline (which sets an `expired` flag the middleware reads once `cancel()` has returned, as that waits for a call being made); once the rest returns, if expired, nothing final was `sent()` and the request's own token isn't stopped (then the server sends nothing), it sends 503 with an empty body (also when the rest threw, then rethrows). Cooperative: it never writes while the handler might (no buffering, unlike Go's `TimeoutHandler`), so a handler ignoring its token delays the 503. The instrumentation goes outside it (it then sees the request's token and the 503; inside, it would record 499). The scheduler is an option (`io::scheduler*`): neither `req` nor `response_writer` reaches it. Measured (stage 4's note): `call_at` costs a request one allocation (the linked source) and about 220 ns pipelined (1116 to 1332 ns), 0.6 to 2 us on a socket; a `sleep_until` task per request cost five allocations (four more: its frame, `spawn()`'s two, and a second source to cancel the sleep) and about 6 us pipelined (a hand-over to the pool per request), 5 us on a socket. `http::client` is the outgoing side.

HTTP/2 is planned in `docs/plans/http2.md` (decided: hand-rolled, on by default; HTTP/3 is parked in `http3.md`). Stage 1 is done: HPACK (`http/hpack.hpp`, internal), a `decoder` and an `encoder` per connection, each with its `dynamic_table`. The static table and Huffman code are generated from RFC 7541's text; the Huffman decoder is a nibble state table built at compile time. The decoder takes a whole header block and calls back for each field (views valid during the call), failing with `invalid_argument` (a COMPRESSION_ERROR) or `value_too_large` (the header list is over its limit: decoded to the end without calling back, to keep the table in step). A `dynamic_table`'s storage is one buffer of the fields' text (appended, oldest first, and moved to its front when it reaches the end) and a ring of fixed-size entries (offset, lengths, hashes of the name and value), both grown by doubling as fields need them, up to twice the table's size and a 32nd of it (stage 5's sixth part): nothing allocated per field, nor at all for a table nothing's added to; `insert()` may copy a field from the table's own (a decoded literal named by index), re-pointing it if the text moves. The encoder (`encoder(hpack::indexing)`) has two modes: `indexing::automatic` (what HTTP/2's sessions use, since stage 5's seventh part; nghttp2's policy, the plan's Decided questions 13 and 14: `sensitive()`'s names and `field::never_indexed` sent never indexed; `:path`, `age`, `content-length`, `etag`, `if-modified-since`, `if-none-match`, `location` and fields over 3/4 of the table literals without indexing; the rest indexed, searched static exact, dynamic exact, static name, dynamic name; its table in step with the peer decoder's, `table()`), and `indexing::none` (the default constructor's, kept for the tests and `fuzz_hpack`, which check representations without the table: static matches, literals without indexing, Huffman coded when shorter; never-indexed fields literal; its table stays empty). `encoder::set_max_table_size()` takes each change of the table's size (growing too, either mode), and the next block starts with the smallest size since the last block, if below what the peer's decoder knows, then the final one, if it differs (RFC 7541 4.2). The sessions hold it to the smaller of the peer's SETTINGS_HEADER_TABLE_SIZE and `session_config::encoder_table_size` (internal, 4096, as Go's, nghttp2's and h2's cap; 0 indexes nothing), so a peer offering more (e.g. Firefox's 65536) costs no size update, and one lowering it gets the minimum, then the final size, in the next block (`test/http/http2.cpp`'s `[session][hpack]` checks the bytes; `[http2][server][hpack]` and `[http2][client][hpack]` the blocks over a socket, recorded by `test::h2_client::blocks`). Its tests decode RFC 7541's Appendix C, and some of hpack-test-case's stories as other implementations encoded them (`test/http/hpack_stories.hpp`, generated by `tools/hpack/gen_stories.py` from a checkout of it; MIT, its notice in the header). Stage 2 is done too: HTTP/2's frames (`http/http2.hpp`: the codec, error codes in `http2::category()`, settings) and `http2::session` (`http/http2_session.hpp`), the protocol without I/O: `receive(bytes, events, now)` takes whole frames (returning how much it used) and reports to a `session_events` interface; `open_stream`/`submit_headers`/`submit_data` (as far as the windows allow)/`reset`/`consume`/`goaway`/`ping`; `take_output()` gives what to write. It's not thread-safe. HTTP/1.1 decoding (`http11.cpp`) is deliberately strict, since an ambiguity between this server and a proxy in front of it is what request smuggling exploits: HTTP/1.1 requests need exactly one valid `Host`; `Transfer-Encoding` must end in `chunked` and can't be combined with `Content-Length`; repeated `Content-Length`s must agree; field lines are validated (no whitespace before the colon, no obsolete folding, no controls in values); and the whole head is limited by `max_header_bytes`, and to `http11::max_fields` (100) field lines, as headers are looked up linearly. When the whole head is buffered (e.g. pipelined requests), it's decoded without a coroutine (`serve_requests()` waits for a head with `fill()` when nothing's buffered, so a head that came in one read is too; `http11::response_decode()` has the same buffered path for a whole, final head, `decode_buffered_response()`, and the client's `send_http11()` waits the same way; a head that isn't all there, or a response starting with an interim one, goes to the coroutine, `decode_reading()`/`decode_response_reading()`); otherwise each line is still parsed as it arrives (so a malformed one fails without waiting for the rest), taken from `buffered_reader`'s buffer in place, which is refilled (`buffered_reader::fill()`) until the line is all there; only a line longer than the buffer is read into a string. `response_encode` (and the client's `request_encode()`/`request_encode_head()`) formats the head straight into the connection's `buffered_writer` (`prepare()`) when it fits, without a coroutine, and so does `response_writer::send()` (which then throws when called, rather than when awaited); otherwise the head is written with one write.

Byte-wise parsing reads from `buffered_reader::buffered()`/`consume()` rather than `co_await`ing each byte; `consume()` only moves an offset (what's left is moved to the front when the buffer is refilled).

DNS's addresses are sorted by RFC 6724; the hosts table's keep its order. `resolve()` isn't a coroutine: a stopped token, a literal (or one of the wrong family: `address_family_not_supported`) and an invalid name (Go's `isDomainName`, but all-numeric names allowed, as `getaddrinfo()` reads them; zones aren't names: `invalid_argument`) are ready tasks. A lookup is a `lookup` (its scheduler, lower-cased name, family and back end; an atomic word, the result, a count of waiters, a `std::stop_source`) and a task spawned on the caller's scheduler (when the caller's task is awaited), running `run_blocking(func, stop)` with the lookup's token, then forgetting the lookup, storing the result, setting the word and `notify_all()`. Concurrent callers share lookups in flight (stage 3, Go's `singleflight` with `ForgetUnshared`): `resolver_state::in_flight`, an `unordered_map` behind its own `mu`, keyed by views of the lookup's scheduler, name (lower-cased in place, and looked up so) family and the back end chosen (so a native and a system lookup of a name don't merge); a caller joins one (`waiters`, under `mu`) or starts one when its task is awaited. The caller waits with `wait_on(word, 0, deadline, stop)`; leaving (an error, or its frame destroyed: a `util::defer`) takes it off the count under `mu`, and the last to leave forgets the lookup in the same step, then stops its source (holding no locks), so no one joins a lookup being stopped (whose `operation_canceled` would be for others' reasons), and a lookup not yet given a thread never starts; one that has finishes on its thread, its result dropped (`getaddrinfo()` can't be interrupted). Nothing is cached: a lookup is forgotten when it finishes. A lookup of both families tells resolutions (`resolver::start_resolving()`, internal, for `connect`: `detail::resolution`, a caller's share left when destroyed, with `look()` (a `detail::found`: the result once done, or the first family's addresses, family and arrival time; and a version), `news()` (the lookup's word, bumped under the resolver's lock each time there's something new, notified only if a resolution has joined: `watched`) and `watch(word, version)` (a word of the caller's to bump too, once: the lookup's `watchers`)) of the first family's addresses as they come in, kept in the lookup for those that join later: the system back end's first call's, or the native back end's (`native_lookup()`'s `found_function`, called by `take_answer()` when a question gets addresses while another of the name's is open). `resolve()` still waits for the result, on `done`.

- `tls/` (with `NET_HAS_TLS`; see `docs/plans/tls.md`): `tls::stream` is a TLS connection over a `tcp_socket` it owns, an `io::reader`/`io::writer` of the application's data, made by `stream::connect()` (a client's handshake, with the host name for SNI and verification) or `stream::accept()` (a server's), each with a deadline. `client_context`/`server_context` hold what connections share (trust store, session cache, certificate and key, policy). Botan stays private: it's a state machine fed the socket's bytes, whose callbacks only fill buffers (under a per-stream mutex, never held across a `co_await`), and the stream does the I/O. Certificates are verified (with the server's name) against the system's trust store by default, or a CA file; `insecure_skip_verification` turns that off. The system's trust store (`system_store()` in `tls.cpp`: Botan's `System_Certificate_Store`, the keychain's on macOS with Clang, the system's bundle elsewhere, read whole; GCC on macOS reads `/etc/ssl/cert.pem`, which lags the keychain: macOS 26.6's lacks AAA Certificate Services and SSL.com's 2022 roots, so example.com's chain fails there, and the public-server tests use www.digicert.com and letsencrypt.org, whose roots every store has; Apple's `/usr/bin/openssl` falls back to the keychain, so it can't show such a gap) is loaded once per process, by the first client context that verifies with it, and shared by every context after (`credentials::trusted` is a `shared_ptr`), as Go's `systemRoots` is: changes to it while the process runs aren't seen (documented in `client_options` and the guide). A CA file's store is each context's own (not shared by path), and a context with `insecure_skip_verification` holds none (a CA file it's given is still read, so a missing one still fails `make()`). Its lookups are safe from several threads at once, as a context's always had to be (a Flatfile store's read maps filled when it's made; the keychain's make each query apart for `SecItemCopyMatching()`); a failed load (e.g. no bundle) fails `make()` and isn't cached, so the next context tries again (the user's decision, 2026-11-01; Go caches the error); a successful one is the only one. So `tls::detail::warm_up()`'s first-time cost is once per process. Tests: `test/tls/stream.cpp`'s `[tls][verification][trust-store]` (contexts of each kind in one process, each verifying with its own; eight made at once on threads, warmed up, then handshaking at once). `bench_tls context make|make-insecure|verify|verify-warm|second|ticker <workers>` measures a context's first load, each in a process of its own (`second`: a second context's make, warm-up and first verification, once the first has read the store). The policy doesn't require revocation data (Botan's default does, which rejects e.g. Let's Encrypt's certificates, as they have none), nor (unless `require_extended_master_secret` is set) TLS 1.2 peers' Extended Master Secret extension (Botan's default does; browsers, Go and OpenSSL don't; `test/tls/stream.cpp`'s `[tls][ems]` handshakes with a TLS 1.2 server without it, `test/tls/no_ems_server.hpp`: Botan's, in the tests, its ServerHello's extension dropped by `tls_modify_extensions()`, asserting from its session that it wasn't used; it replaced badssl.com, which reset CI's connections). TLS 1.2's renegotiation is refused on both sides by ending the connection: the policy's `abort_connection_on_undesired_renegotiation()` is true (Botan's default, false, answers with a warning-level `no_renegotiation` and goes on; RFC 9113 9.2.1 makes it a connection error for HTTP/2, and Go fails any connection), so Botan throws from `received_data()` and sends a fatal `no_renegotiation` (100): the refusing side's reads (and writes after them) fail with `sent_alert_base` + 100 (there's no `tls::alert` condition for it), the peer gets the fatal alert, then the end of the connection; an HTTP/2 connection can't send GOAWAY first (TLS has failed). Tests: `test/tls/renegotiation.cpp` (`[tls][renegotiation]`: a client renegotiating with `stream::accept()`'s stream and with `http::server` over HTTP/1.1 and HTTP/2, a waiting handler stopped; a server's HelloRequest to `stream::connect()`'s), through `test/tls/botan_peer.hpp` (Botan's TLS 1.2 client or server over a cppnet socket, driven a step at a time: `handshake()`, `send()`, `receive()`, `renegotiate()`, `read_to_end()`, recording the alert received; Botan fails on application data while renegotiating, so the HTTP/2 test reads the server's frames up to its SETTINGS ACK first). Both contexts allow TLS 1.2 and 1.3 unless `min_version`/`max_version` (a `tls::version`, as Go's `MinVersion`/`MaxVersion`) narrow them: our policy overrides Botan's `allow_tls12()`/`allow_tls13()`, the client offers the latest it allows (`latest_supported_version()`), and `make()` fails with `invalid_argument` if min is after max; with none in common, the server sends `protocol_version` (either way round), so the client's error is that alert from the peer. `stream::version()` is the version agreed on (recorded by `tls_session_established()`), which the HTTP server gives handlers in `server_request::tls_version`. `tls::version` (`none` = 0, `tls12` = 0x0303, `tls13` = 0x0304: the wire values, so `none` sorts first) is in `include/tls/version.hpp`, which needs neither Botan nor `NET_HAS_TLS` (only `src/tls/` is skipped without TLS; `include/` is all on the include path), so `http/request.hpp` includes it in every build; `make()`'s check (`valid_versions()`) refuses `none` as either bound. `test/tls/server.cpp` checks the version a handler sees over TLS 1.2 and 1.3 (the client limited to one) and in cleartext, over HTTP/1.1 and HTTP/2; `test/http/server.cpp` checks cleartext's `none` in every build, without TLS too. Botan endpoints agree on 1.3 unless one is limited, so the TLS 1.2 tests limit one side (`test/tls/stream.cpp`'s version tests, and in `test/tls/server.cpp` the pool's reuse, HTTP/2 over ALPN, and a client's close_notify or end stopping a handler). The peer closing without `close_notify` is `tls::errc::stream_truncated`; the peer's close_notify is answered with ours (Botan's default), so nothing more can be written after reading it. Flushing ciphertext is a queue: one task writes at a time, and a write (or `shutdown()`) that finds one writing waits for it (a `coro::notifier`, on the socket's scheduler's pool, `socket::get_scheduler()`) as far as its own data, so every write returns only once its data has gone, limited by the socket's write deadline and timeout; a read's replies (alerts, key updates) don't wait, but leave them to the writer in progress (waiting could deadlock against a peer that's waiting for its writes to be read). A failed write is kept (`write_failure`: part of a record may have gone), and every later write returns it. A write over `write_batch` (the context's `write_batch_size`, 64 KiB, at least 16 KiB, kept in `client_state`/`server_state` and copied into each stream's `detail::connection`, as its last member: 8 bytes among the flush's members made writes 15% slower, cache lines it seems; the plan's "Learned after stage 9: configurable sizes") is encrypted and flushed a batch at a time (`connection::write_batched()`), so it holds a batch's ciphertext at most (a 16 MiB write held about 48 MiB before; `bench_tls writes` measures it, the plan's websockets "Learned after stage 9" has the numbers); writes stay whole and in call order through turns (`write_turn`: a ticket taken when `write()` is called, `turn_now`/`turns_given`, ended once, by the write or its task's destruction, `turns_skipped` for those ended early), which a write called while any has a turn, `shutdown()`'s close_notify and `wait_writable()` take and wait for; a small write with no turns waiting is encrypted at once, as before. Tests: `test/tls/stream.cpp`'s `[tls][write][batches]` (and `write_batch_size` seen through a relay between client and server that notes the records' lengths: a batch is encrypted whole, as 16 KiB records but its last, so 20 KiB batches are records of 16 and 4 KiB; and `make()` refusing under 16 KiB). The HTTP client's pool reuses an idle TLS connection only if `tls::detail::idle_clean()` (nothing decrypted and unread, no part of a record fed to Botan, which the stream tracks from the records' framing itself, no close_notify, no failure) as well as its socket peek. `stream::shutdown()` sends close_notify without closing the socket (reads still work); `connect()`/`accept()` take an optional `std::stop_token`, which ends a handshake (`operation_canceled`) by shutting the socket's reading side. Session resumption (`docs/plans/tls.md`, stage 4's third part): TLS 1.3 only, with tickets from `ticket_manager` (cppnet's `Botan::TLS::Session_Manager`, in the server's state; `server_options::session_tickets`, on by default, `session_ticket_lifetime` (24 h, at most 7 days), `session_ticket_keys`, `server_context::set_session_ticket_keys()`): `Session::encrypt()` with the first key, each tried on a ticket; keys random (rotated lazily each lifetime, the previous kept to two lifetimes) or given (no rotation), each derived (HMAC-SHA-256) with the context's client authentication (mode and client CAs' DER), so a ticket from a context verifying clients differently doesn't decrypt; a session whose client leaf has expired, or without a certificate where one's required, isn't resumed; `emits_session_tickets()` is false, so TLS 1.2 never mentions tickets. `stream::resumed()` (from `tls_session_established()`). A resumed session's `peer_certificates()` are the session's. The client's sessions are `client_sessions` (Botan's in-memory cache, 1000, wrapped: Botan 3.12 stores TLS 1.3 tickets as opaque handles that its `remove()` can't find, so tickets were never used up; the wrapper stores them as tickets, so each is offered once; fixed upstream by Botan's PR #5847, commit 33a901803c, after 3.13.0: when vcpkg's baseline or the overlay moves to a Botan release with it, drop the wrapper, keeping its test that each ticket is offered once), keyed by `Server_Information{host, port}` (the socket's peer port). Tests' hooks: `tls::detail::make_server_context(options, server_hooks{clock, handshake_done})` (a clock for ticket ages, rotation and client certificate verification; a callback with each handshake's `handshake_details`: whether it resumed, TLS 1.3's group (code point, from `Session_Summary::kex_parameters()`) and whether a HelloRetryRequest was sent (seen by `tls_inspect_handshake_msg()`), which `http::server` doesn't expose). Tests in `test/tls/resumption.cpp` (streams) and `test/tls/server.cpp` (through `http::client`, `idle_timeout` 0 so each request connects). Alerts are errors in `tls::category()`: the peer's by their TLS codes (e.g. 42), those sent to the peer at `sent_alert_base` (512) plus the code; a certificate that failed verification is in `verification_category()` (Botan's `Certificate_Status_Code`, whose text is the message; recorded by our `tls_verify_cert_chain`, which does what Botan's does). Client certificates (mutual TLS; `docs/plans/tls.md`, stage 4's second part): `server_options::client_auth` (`none`, `optional`, `required`: both verify what's sent) with `client_ca_file` (needed unless `none`, refused with it; never the system's), and `client_options::certificate_chain`/`private_key` (both or neither; `http::client` gets them through `client_options::tls`); one `credentials` manager for both sides (its side's type, `"tls-client"`/`"tls-server"`, names the CAs it trusts for the peer, null for a server that doesn't ask, so nothing's requested, and its own chain and key), whose `find_cert_chain()` sends a client's chain only if its key's kind is asked for and (if the server names CAs) one of its issuers is named, as Go's `SupportsCertificate`; the policy's `request_`/`require_client_certificate_authentication()` follow `client_auth`. A refused client certificate fails a TLS 1.2 client's `connect()`, but in TLS 1.3 the client's first read (its handshake is done before the server looks). `stream::peer_certificates()` (a `shared_ptr<const std::vector<tls::certificate>>`, never null: none is a static empty vector, not allocated) is made on first call (under the stream's mutex) from the chain kept when the handshake completed, then shared; `tls::certificate` (`include/tls/certificate.hpp`, Botan-free, built without TLS too, as `tls/version.hpp`) is plain data: the DER, `subject`/`issuer` as RFC 4514 writes them (formatted by cppnet from the name's DER, keeping multi-valued RDNs; other attribute types as `OID=#hex`), `serial_number` (upper-case hex), `not_before`/`not_after` (clamped to the clock), SANs (sorted per kind), SHA-256. An HTTP/2 connection whose read fails with a TLS alert (`detail::tls_failure()`) fails its streams with it (`end(why)`, rather than `connection_aborted`, so the client doesn't retry them as dropped); a write (or the writer's wait for the socket) that fails with a TLS failure ends it with that too (`write_failed()`: once the reader has taken the peer's alert in, the stream's writes and waits return it, so the writer could get there first and fail the streams as cut off, which CI caught once; `test/tls/server.cpp`'s writer test fails the client's `http2_writable` hook with one once the request's handled); and a write that fails with `status_condition::closed` leaves ending the connection to the reader, which finds why (an alert the peer sent before closing) at once.
